## Confirmed audit

The local/server Cook has only private `notes`; public text is `Dish.publicDescription` / `dishes.public_description`. `social_posts.post_description` is a separate editable caption with exact `(author_id,source_attempt_id)` linkage. New/Edit Cook overwrites the shared Dish text. The client `PublicDescriptionSync` fans one Dish text across up to 20 cooks, and maps posts back through title-narrowed lookup. This can overwrite intentionally different captions, misses renamed Dishes and older cooks, and is not atomic across devices. Pass-only caption edits do not advance the cooking sync revision. Private cook/Dish notes are separate and must remain so.

Read-only hosted aggregate audit November 20, 2026: 46 active cooks, 14 Dishes with text, 18 active posts, nine with captions, zero missing Cook associations. Seven active post/Dish values differ: one pair of different nonempty texts, three Dish-only, three caption-only; five nonempty pairs agree. There are 13 retired posts and three cooks with different historical captions. These counts overlap and are not an author-intent determination. No caption or private note text was returned/logged; no hosted rows changed.

## Contract handoff to Claude — implement against this boundary

- Canonical new field: `CookingAttempt.publicDescription: String?` ↔ `cooking_attempts.public_description` ↔ attempt sync `publicDescription`. At most 2,000 Unicode scalars, permitted paragraph controls. **nil = legacy/unresolved; empty string = deliberate clear**. Missing/null in an old sync write preserves an existing canonical value. New cooks start with their own text, never inherit/overwrite sibling/Dish text. Private `notes` / Dish `privateNotes` stay private.
- Existing graph/outbox owns local edits and persistence. Codex provides `CookingStore.editCookDescription(_:publicDescription:context:)`. Change the Cook's text, not the Dish, then let ordinary structured sync update the post read projection. An unchanged Save creates no operation.
- Pass cards keep `postDescription`, now read from the linked Cook when canonical; unresolved old posts retain their exact stored caption. `sourceAttemptID` is returned **only to the author**, so the editor can locate the exact local Cook without title matching. Other accounts never receive private Cook IDs.
- Remove Dish-wide caption fanout and Dish writes from `DishTextEditor`, `SocialPostActions` and `SocialShareView`; these are Claude-owned. `PublicDescriptionSync.pushToPosts(of: Dish)` is retired and will no longer fan out. A new Cook and each composer use that Cook's text. Existing publication confirmation remains required.
- Legacy text is not guessed or backfilled. A read-only owner `cook_description/get {attemptID}` exposes canonical text plus bounded legacy Dish/post evidence and `needsReview`. `effectiveDescription` matches the active legacy post caption (even blank), else the old Dish text for an unposted Cook. It is a display fallback, not a silently saved canonical value. For a legacy edit draft use `draft.useLegacyDescriptionContext(context)` after loading, so merely showing the fallback does not count as a description edit when another metadata field is saved. It validates the exact Cook and refuses to apply a remote canonical value to a legacy draft; reconcile/restore current server state first in that case. After explicit owner Save, the canonical field wins everywhere; historical caption/Dish columns remain intact.
- Old explicit `social_content/editDescription` remains supported as an exact-Cook edit, without changing stored legacy captions or siblings. A real change increments the existing account sync revision once. Retries/unchanged text make no extra write. Prepare retries never edit an existing post/Cook. A legacy composer caption is adopted only for a new post whose Cook is still unresolved; it cannot overwrite any already-canonical value (including an intentional clear). Claude should save the exact Cook through its journal and wait for sync before preparing/publishing, preferably omitting `postDescription`. New callers can supply field-level `expectedDescription` for PT409 protection.
- New frontend behavior requires this migration before activation/distribution. The existing account/revision receipt adds `cook_description_version: 1`. `SupabaseCookingSyncTransport` probes through normal provisioning only if needed, caches positive support for the current Auth identity, and refuses to send a new description to a server that omits support. It keeps the original immutable operation pending using existing bounded unavailable/backoff behavior. Legacy operations without a non-null field keep their old path; no extra routine probe or background job is introduced. Confirm deployment/capability before enabling the coordinated UI. There is no production rollout in this cycle.
