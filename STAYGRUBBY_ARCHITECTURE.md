# StayGrubby — current product and architecture

**Canonical current-state overview — updated November 4, 2026.** Read [AGENTS.md](AGENTS.md) for development rules and the [Master Roadmap](STAYGRUBBY_MASTER_ROADMAP.md) for planned work. This overview reconciles the implementation and owner decisions; dated domain/review sections remain evidence for their checkpoints, not claims that their old counts, gates or future boundaries still apply.

## Product and navigation

StayGrubby is a food/cooking platform centered on comparison-based ranking of things people actually cook, a personal cookbook/Recipe experience and explicit social sharing.

**Cook → Rank → Remember → Share → Interact**

**DISCOVER → SAVE → COOK → RANK → REMEMBER → SHARE → INSPIRE**

Cooking, saving a Recipe and publishing a social post are separate actions. Saving/discovering does not mean something was cooked/ranked. Popularity never changes personal ranking.

The native SwiftUI/SwiftData iPhone application targets iOS 26.5 and supports **upright portrait only**, with light/dark appearance and accessibility within portrait. Project/target/scheme/module is `StayGrubby`; bundle ID is `com.guyrettig.StayGrubby`.

The four authenticated tabs are **Grub List / Grub Rank / Food Bible / My Kitchen**; Grub Rank is initial. My Kitchen contains authorized own social posts, identity, Signature Dishes, Sous Chefs and Settings. Tickets are deliberately hidden from normal V1 navigation; their underlying implementation/data remain preserved.

## Domain boundaries

| Domain | Current implementation and ownership |
| --- | --- |
| Dish | Stable cooking identity/name, default Course/Cuisine/Source, optional Public Description and owner-private Dish notes; no independent score |
| CookingAttempt | An actual cook/version of a Dish: date, optional version title, private notes, Course snapshot, tags and cook-owned media |
| RankedItem | Unique ranking identity per attempt; holds estimated strength/uncertainty and display diagnostics |
| Ranking evidence | One global cooking RankingList with individual immutable-ID Comparison observations; evidence is authoritative |
| Recipe | Server-owned UUID, owner/visibility, structured content, current revision; private current cook links and legacy Dish-family links are separate relationships |
| Recipe history/provenance | Stable current identity, immutable archived content, restore-as-new revision and exact snapshots for explicitly associated cooks; Dish linkage alone is not proof a historical cook used the latest Recipe |
| Social | Optional profile, mutual friendship, explicit posts/safe snapshots, Hands/comments, invitations/recreations and notifications |
| Account/media | Apple/Supabase identity maps to permanent account; account-isolated working store, structured outbox and private photo backup |

### Cooking library

New Dish and New Version both create an independent attempt/item in the same global ranking. Edit and re-rank preserve existing attempt/item identities. Top Version / All Versions are projections, preserving true global ranks; filters do not create another ranking.

Course uses the controlled existing options. Dietary, Contains, custom tags and legacy free-label compatibility remain distinct in storage. Custom Tags are hidden from normal entry/detail/search; historical values and backend compatibility remain. Halal is hidden from Dietary selection while its stored code/values remain compatible. Avoid is a presentation/filter selection over existing metadata, not a medical guarantee. Cuisine uses stable canonical IDs plus account-owned custom values; no inference/backfill into existing Dishes is implied. DishSource is optional manual inspiration/attribution with My Own, Cookbook, Online, Restaurant, Friend / Family and Other UI choices; legacy storage codes remain compatible. It is separate from Recipe creator/source attribution.

All personal cooking mutations go through the existing cooking/ranking services so references, evidence cleanup and durable synchronization remain consistent. Do not directly delete domain rows as a shortcut.

### Ranking — accepted and frozen

Initial Liked / Fine / Didn't Like assessment, adaptive comparisons, Too Tough ties, Skip and Undo feed the established ranking workflow. Bradley–Terry uses retained individual evidence, including repeated observations; re-rank adds evidence to the same item. The engine uses Foundation/Accelerate independently of SwiftUI, SwiftData, Recipes and social services.

**Order and displayed score are related but distinct.** Order comes from fitted strengths. The accepted reaction-conditioned `ScoreCalibration` supplies the current displayed score; the older relative diagnostic transform in the technical specification is not the current UI mapping. Reactions do not rewrite the Bradley–Terry objective. See [RANKING_MODEL.md](RANKING_MODEL.md) and [calibration details](STAYGRUBBY_PRODUCT_STRUCTURE_SCORE_REVIEW.md), rather than duplicating formulas here.

Numerical scores unlock at ten eligible saved ranked attempts/versions. Re-rank does not increment eligibility; deleting below ten relocks presentation without destroying evidence. UI, accessibility, previews and exports obey the gate. Native numerical colors are muted coral 1.0–4.9, orange 5.0–7.5, gold 7.6–10.0; exported card scores always use brand red. Recipe/social work must preserve all ranking, calibration, evidence and visibility behavior.

## Food Bible and Recipes — Architecture V2

Recipe means **how I make something**; Dish means **what I cooked/ranked**. Either exists alone. Food Bible now indexes Recipe UUIDs, including standalone owned Recipes and eligible Recipes explicitly linked to the caller’s Dishes, exactly once. Multiple retained links do not duplicate cards. Existing UUIDs, content, history and links are preserved without backfill or copying. Older cookbook endpoints remain compatible; the new bounded `library_index` uses Recipe UUID pagination.

Food Bible Add Recipe offers **Paste Recipe / Add Manually**, neither requiring a Dish. Recipe Detail keeps Cook Recipe primary and compact sharing/native Recipe actions for Edit, Version History, Save as New, link/change/unlink, Send and Delete as authorized. Normal linking reuses the photographic Dish chooser followed by the shared version/date rows: **Dish → specific cook**. Dish Detail links/creates for its actual cook. New Recipe creation and exact linking are atomic; a conflict leaves no orphan Recipe.

Stage 4 adds owner-private `recipe_cook_links`: one current cook per Recipe/account and one current Recipe per cook. Current linkage is a deliberate association, not proof the Recipe was used historically. Compare-and-swap guards reject stale edits; current access, active account/session and own active cook are required. Raw table access is closed under RLS. No legacy `dish_recipes` link is backfilled/deleted/reinterpreted. Legacy-only readers explicitly say Dish family/no specific version; removing an exact link preserves any separately retained legacy link. Deleting a selected cook cannot silently choose another version.

Cook Detail distinguishes **Recipe used** (immutable content/revision) from a deliberately **Linked Recipe** or legacy family link. The actual completed snapshot takes precedence over legacy inference when no current link exists. Completing an explicit Recipe cook may establish a current exact link only when neither endpoint already has one; it never moves an existing choice. Historical snapshots remain readable after source editing/revocation/deletion under the existing owner boundary. Owned sharing choices prefer the actual Recipe-used revision, then exact current link, then legacy compatibility; foreign snapshots never grant sharing rights.

Recipes use authenticated online APIs with ownership/visibility and expected-revision guards, not a second offline SwiftData cookbook. Personal cooking remains locally usable offline. Food Bible search/filter/sort stays local over bounded authorized pages, including unlinked Recipes, descriptions and Recipe metadata, with compatible linked cook/Dish fallback for absent Course/Cuisine. Shared filter sheets support Course, Cuisine, Contains, Avoid, literal manual Source and Recipe-photo presence; groups compose with search and directional Recipe creation-time/name sorting (Recently Updated retained). Unknown metadata stays unknown; Avoid excludes known/possible selected allergens without a free-from guarantee. There is no reviewed Recipe Dietary field, so no Dietary claim/filter is invented from cook tags. Custom Tags stay hidden. Recipe cuisine/Course leads Food Bible; Dish cuisine/default Course and actual cook assertions still lead Grub Rank and current cooking-post snapshots. Recipe edits do not overwrite Dish/cook metadata or change ranking/filter semantics. Explicit Recipe-to-cook draft prefills remain reviewable.

`RecipeContent`/editable `RecipeDraft` retain stable component/ingredient/step IDs, legacy compatibility and exact rational quantities. Optional short description, yield, times/origins, Course/Cuisine, source/creator/link/tips and allergens remain Recipe-owned. Recipe description is editable/removable, with guidance for 1–3 useful sentences. Reviewed Recipe Contains/Possible is the primary ingredient-derived allergen surface. Existing cook-specific Contains/dietary/legacy tags are retained under cook-specific controls and remain searchable/filterable; no guessed metadata migration, religious inference or medical guarantee is introduced.

Normal Save keeps the Recipe ID, checks current revision and archives a new immutable content revision. History is owner-only and paginated. Restore copies archived content exactly into a **new** current revision, preserving current audience and prior history (including legacy flat content and photo references). Save as New opens an independent private draft/identity/history. Stale editing cannot silently recreate a deleted Recipe. Exact RecipeCook revision/content snapshots remain immutable through later Recipe edits/restores; an explicit cook association is ownership/revision checked and cannot replace a different existing snapshot. Never infer which Recipe an old cook used from today’s Dish link. Detaching/deleting Recipes preserves independent cooking/evidence and retained cook snapshots.

Reader serving adjustment is a deterministic **display-only** projection over the existing exact rational quantity parser. Usable canonical serving counts (plain counts or explicit serves/servings/people/portions, 1–100) enable adjustment; ranges/loaf yields/vague yields do not. Integer/fraction/decimal/count/metric/US-volume/range quantities scale proportionally without unit conversion. Unmeasured, ambiguous, to-taste/as-needed and per-person quantities stay written; source methods/times stay canonical. Changing displayed servings never saves quantities or changes historical snapshots. There is no AI scaling math or requirement for Creator to invent yield.

Recipe-owned optional photos take precedence over the explicitly linked cook, then the branded fallback. A loading/unavailable owned photo does not flash a different cook image. Only legacy family-only links may use the deterministic representative-cook fallback. Cook, Recipe, revision and immutable snapshot photo IDs remain independent; linking, replacing or removing one never transfers ownership or rewrites another photo. `LocalPhotoStore.prepare` supplies metadata-stripped optimized JPEG bytes; existing account-generation-guarded media transport adds the private `recipe-photos` bucket. Server-owned immutable manifests bind account/asset/path/hash/size; a verified upload completes before a Recipe can reference it. Download checks SHA-256/JPEG bounds. Photo bytes are separate from cooking media and do not alter its sync. Current friends can read a photo only through an accessible current Recipe; history is owner-only. Old referenced photos survive replacement/removal for archived revisions/cook snapshots; a bounded owner-authorized RPC/Storage policy supports unreferenced upload cleanup, and account deletion clears all Recipe bytes before graph/Auth erasure. The new bucket starts empty; no existing media is moved.

Ingredient entry/paste and native within/between-component row ordering are unchanged. Explicit Save, revision conflict protection, dirty/cancel protection and editable import review remain. Unsaved force-quit recovery is not claimed. See [Architecture V2 verification/release state](FOOD_BIBLE_ARCHITECTURE_V2_REVIEW.md); the owner accepted Food Bible Architecture V2, independent identities, revisions/photos, deterministic scaling and review-before-Save at the start of the Recipe + Social Integration cycle (November 2). These systems are frozen except for evidenced integration defects.

Stage 4 reader units **As Written / US / Metric** are a pure display projection composed with existing exact serving math. NIST customary factors convert only recognized mass→mass or volume→volume; no density, count-unit, per-person, to-taste or as-needed guesses. Converted values carry ≈ and cooking-scale rounding; fractions/ranges, preparation and uncertainty remain, while instructions/temperatures/durations stay as written. Unsupported/legacy unsplit ingredient amounts remain unchanged. Repeated switching starts from canonical content, never converted output, and never saves a revision. Recipe/Dish editors share manual attribution fields and the accepted Cuisine selector where semantics match; Recipe attribution stays freeform, Dish Source stays structured. The broader Sous Chef/metadata taxonomy remains future work.

Future My Recipes (owned) versus Saved Recipes (bookmarks to another creator) is a roadmap distinction, not current bookmarking implementation. Save as New/private copy remains an independently owned identity with provenance. Recipe Box is not confirmed terminology. See [Stage 4 evidence and owner acceptance](NEXT_RELEASE_STAGE_4_REVIEW.md).

### Recipe Creator — Gemini-first, contract 4

**Messy input → Gemini understands/constructs a structured Recipe → technical validation → editable RecipeDraft → user review/edit → explicit Save.** Source text is context for Gemini, **not a vocabulary whitelist**. This permanent November 2 owner decision supersedes the former lexical guards and source-reconstruction recovery, including v19–v26 assumptions in historical reviews. Earlier V1/refinement physical acceptance remains historical evidence; existing Recipe/cooking ownership and deterministic serving adjustment remain intact.

Gemini owns culinary interpretation, correction of clear speech noise, professional prose, meaningful sections, ingredient allocation, chronology, title/short description, cuisine/allergen proposals and reasonable optional yield/time estimates. It should preserve supplied amounts, per-person bases and useful preparation details, avoid invented precise quantities/settings, and keep uncertainty/options clear. These are model/content-review responsibilities; StayGrubby does not attempt to prove them by matching source words, phrases or tokens. Minor imperfect editorial choices do not block a useful draft. The user is the final content reviewer.

The transport returns title, optional description/yield/source/metadata, and components with ingredient **lines**, ordered instruction **strings** and optional explicit prerequisite indexes. Ingredient lines naturally retain amounts/units/preparation/alternatives, then the existing exact IngredientParser maps them into native fields without changing serving math. Contract 4 adds description directly to the existing RecipeContent description; contracts 1–3 remain structurally accepted, with no new description field sent to older clients. Updated native code requests contract 4. Old installed clients with lexical guards need the latest build; no distribution/upload is implied.

StayGrubby validates bounded JSON/types/core arrays, nonempty usable content, supported metadata/enums, component/row/text caps, corrupt quantities and valid acyclic/in-range explicit dependencies. Only dependency ordering is applied, not inferred chronology. Invalid optional metadata/description is omitted, missing metadata remains unknown, and estimates/provenance need no literal source quotation. Inconsistent optional totals are cleared. Provider prose, names, ingredient allocations, duplicate rows and method text are preserved; no source-based reconstruction, ingredient extraction from methods, deduplication, modifier repair, fact-lock or second AI judge remains. Native mapping enforces the existing 40 KB save-compatible draft bound; Review never saves automatically.

Gemini remains the standard consented Paste Recipe provider; Apple infrastructure remains dormant in normal creation. Request/provider/output/field bounds, JWT/live-session ownership, server-only key and 3/account/minute abuse protection remain. There is no daily product cap, recurring date/30-day expiry, billing setup or automatic provider retry. Provider cooldown retains friendly Cloud AI messaging and manual/deterministic fallback. First-use external-AI disclosure/account-scoped acknowledgement and Add Manually are unchanged. Saved Recipe identities/revisions/photos, cook snapshots, ranking, social data and serving projection were not altered.

**Deployed v27 / JWT enabled** implements this boundary. Retained real French-toast, Shakshuka and kale outputs all map offline; three separately authorized fresh v27 calls also returned usable drafts with descriptions, and their actual responses passed native edit/serialization checks. All **3/3** new calls are consumed; the earlier 6/6 and 3/3 ledgers are unchanged. Final focused evidence: 69 function tests, 4 budget tests, 22 distinct native tests /28 executions pass. No broad UI/backend or Release suite. Drafts are not perfect: bread-count/temperature interpretation, chile specificity, equipment in an ingredient list or wording may need owner edits. That is not a claim of kitchen testing, source-perfect output or physical acceptance. **OWNER ACCEPTED** at the start of Recipe + Social Integration (November 2); the dated pending phrase records the previous checkpoint only. No model tuning or new provider calls are part of integration. See [dated evidence and one owner test](FOOD_BIBLE_ARCHITECTURE_V2_REVIEW.md#november-2--gemini-first-architecture-correction).

## Accounts, private sync and media

Production flow is onboarding → native Sign in with Apple → Supabase authentication → permanent account resolution → verified account-store readiness → authenticated app. New real accounts start empty; sign-out returns to onboarding. Session restoration is implemented; brief cold-start transition polish remains separate. No production guest mode. Debug development-library access is compile-time excluded from Release, isolated and unable to authenticate/provision/upload as a real account. Physical device-local development storage is separate from the Simulator library.

SwiftData is the local working cooking store. Mutations atomically persist domain changes plus durable outbox operations; authenticated owner-derived RPCs provide receipts, expected revisions, retries, snapshots and restoration. Hydration preserves identities/numeric evidence without refitting/reranking or creating upload intent. Existing conservative conflict rejection is deliberate; new conflict merging is not implemented. Tombstones/causal history prevent deleted cooks from resurrecting; raw server row counts need not become zero after deletion.

Local cook photos use account-scoped file roots and metadata, with optimized display/thumbnail variants privately backed up/restored using immutable account/media/hash paths and validated bytes. Profile reports pending/current state and retry. Social and avatar media have separate private buckets, permissions and cleanup. Test UUID stores/media roots must never write into the normal account/guest/demo roots.

Private application tables have RLS and least-privilege grants; narrow server APIs derive permanent ownership from a verified live session. Client-safe Supabase configuration is distinct from privileged server credentials. Store readiness and generation/cancellation guards prevent account-switch/stale-response leakage.

Coordinated account deletion is implemented: deliberate native confirmation/fresh Apple verification, server-side Apple verification/revocation and idempotent staged private/social media, database, Auth and local cleanup. The real physical Apple revocation/deletion test is intentionally deferred, **not a blocker to ongoing development**. Never perform it against the owner's account as routine verification.

## Recipe + Social Integration — current contract

Recipes remain independent, private by default and optional for cooking/posting. A Dish link, AI creation, actual cook or automatic cook-post preference never opts into Recipe sharing. The existing Recipe editor controls `private` / current `friends` visibility. A composer’s OFF-by-default **Include Recipe**, or the author’s **Recipe Sharing** action on a post, deliberately enables friends visibility and attaches one chosen archived revision. The consent includes that revision’s Recipe photo and Recipe fields, never Personal Notes/private cooking photos. A linked current Recipe is labeled as such, not falsely presented as proof of what was cooked; a caller-owned explicit completed cook snapshot takes precedence. A foreign snapshot cannot delegate its creator’s Recipe; an independently owned linked copy can instead be offered without rewriting the historical cook. Recipes owned by someone else cannot be delegated through your post: save an independent copy first.

`post_recipes` references existing `recipe_revisions`, not another content store. Grub List stays chronological and post-centered: Hands/comments/reports/notifications belong to the post. The shared reader resolves by **post UUID**, reauthorizes post visibility plus Recipe sharing/ownership, and returns only the selected revision, creator/cook attribution and an authorized social-photo fallback. No owner editor, private history, revision browser or local private-Dish media is exposed. Description, ingredients/components, yield/timing/Cuisine/allergens and display-only serving projection reuse the normal reader. Later Recipe edits or Dish unlinking do not alter the selected revision or historical cook evidence. Existing posts gain no inferred attachment during migration.

Run It Back and Shared Cooking reuse their existing independent recipient item/claim/outbox/rank flows. Only an explicitly shared accessible post attachment may supply the Recipe snapshot; an invitation alone grants none. Attribution stays separate from cooking/ranking ownership. A recipient can **Save a Private Copy** explicitly: a new owned Recipe/revision-1 identity, exact shared content/description and `recipe_forks` provenance (original Recipe/revision/creator/post); no shared mutable ownership. Source-authority metadata is server derived. Foreign Recipe photo IDs are omitted from a copy rather than transferring photo ownership or duplicating uploads; add an owned photo if desired. A saved Recipe has identical downstream behavior whether created manually or through accepted Creator review.

Privacy is enforced by closed/RLS tables and owner-derived APIs, with fixed-search-path private helpers and no raw client table access. Shared reads/photo reads respect current friendship, both-direction blocks, account/profile/moderation state, Recipe visibility and post deletion. Turning Recipe visibility private revokes all further friend Recipe reads; removing an attachment revokes that post’s reader/future Recipe transfer but does not implicitly change Recipe-wide visibility. Deleting a post removes post-based access, not an independently friends-visible current Recipe. Deleting the source Recipe removes live attachments/history access; source references in private forks are nullified. Unlinking a Dish does not revoke an already deliberate share. Existing independent private copies/recipient cook snapshots cannot be recalled or rewritten. Loaded social content clears on background/refresh/error; no real-time remote erasure claim.

Recipe-owned images precede separately consented social cook photos, then the existing fallback. The private `recipe-photos` policy permits an archived image only through an active explicit attachment or existing current-Recipe authorization. Unshared unrelated revision images remain private. Original private cooking-media authorization is untouched. No new upload bucket, provider call, photo transport, social interaction system, notification kind, ranking behavior or final UI redesign is introduced.
