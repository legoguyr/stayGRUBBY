## Creator architecture

One provider generation → strict structure/procedural fact guards → supported construction and metadata normalization → original source qualifiers/facts → existing editable RecipeDraft/Recipe Editor → explicit Save. No second AI polish call. Gemini requests use `contractVersion: 2`; older clients retain the source-only request/schema path so existing installations are not handed an incompatible envelope. Both versions retain auth, consent, bounds, redaction and a single provider call.

The common instructions ask an intelligent cookbook editor to recognize preparations, resolve clear self-corrections, consolidate redundant mentions while preserving measured allocations, order preparations before their use, write imperative prose, propose useful yield/time estimates, and classify conservatively. Chronological component dependencies are transient zero-based indexes, sorted deterministically and rejected when invalid/cyclic. Simple recipes stay one component. Within-component identical **unmeasured** repetitions may consolidate; separate measured quantities are never added or silently merged. Measured ingredient facts already present in the method can fill a missing/unmeasured ingredient row only after source grounding. Explicit same-ingredient “3 eggs, no, 2 eggs” corrections use the resolved factual source; original input is never altered or discarded.

Procedural boundaries remain: no new major ingredient/substitution, materially different technique, unsupported exact ingredient amount, procedural temperature/duration, mandatory replacement of an option, or confident guess at an uncertain ingredient. Metadata estimates never become procedural instructions. Original text/review/manual correction remain available. Deterministic validation is bounded evidence checking, not formal proof of arbitrary language, complete ingredients, component assignments or a model's culinary judgment.

## Metadata and honesty

Transient metadata proposals carry `value`, `origin` (**provided / derived / estimated / unknown**) and a source excerpt. Canonical cuisine and nine allergen codes reuse existing taxonomies. Invalid attribution/provenance or unsupported classifications become unknown; malformed structure fails safely. An estimate cannot claim to be user-provided. Explicit overall serving/prep/cook/total labels override generic model guesses, including deterministic hour-to-minute equivalence. Fractional minute metadata rounds upward and is marked derived; procedural text retains the original duration. A separately timed crisp is not silently declared the entire recipe cook time.

Useful yield/prep/cook/elapsed suggestions are allowed and editable. Per-person quantities are not scaled to force a serving count. Provided yield units such as “1 loaf” remain yield, not a fabricated count of people. Total can follow parallel workflow; it must be at least each active prep/cook duration. When valid overall prep/cook values exist with no parallel-work indication, their total is derived. Unknown Creator totals stay unknown rather than blindly adding parallel durations. Legacy recipes retain their prior fallback display.

Permanent Recipe JSON adds only optional `elapsedMinutes`, compact `metadataOrigins`, and ingredient-based `allergens`. Source excerpts/provider objects are transient; raw dictation is not newly stored in revisions. Existing flat arrays/components, IDs, revisions and Save API stay authoritative. Opening legacy data does not backfill it. User edits clear the corresponding generated origin. New fields survive normal revision/snapshot/restore paths. Cookbook summaries carry elapsed time and distinguish Creator unknown totals from legacy sum fallback.

Cuisine suggestions use the existing 26 broad canonical labels, never a new global taxonomy or forced hyper-specific region. Ambiguous/fusion input may remain unknown. Manual cuisine correction remains possible, including existing custom values.

Allergens come primarily from deterministic ingredient rules using existing codes: peanuts, treeNuts, sesame, milk, egg, wheat, soy, fish, shellfish. For example Parmesan/butter → milk, tahini → sesame, mayonnaise → egg. Generic pasta/flour/product-dependent ingredients require possible-allergen/label review; optional/alternative allergens remain possible. Unsupported model hints cannot create an allergen claim. The editor permits review/correction, and ingredient changes trigger a fresh assessment. Reader/editor explicitly say this is **not an allergen-free or cross-contact guarantee**. No kosher/halal/religious certification or dietary-free status is inferred. Existing user-entered cooking tags remain separate.

## Providers and observed Apple capability

Both providers target identical culinary/construction/metadata semantics and the same final RecipeDraft. Gemini uses the versioned proposal envelope. Apple uses a flatter `@Generable` schema mapped into those same proposals in a single model call; this avoids a nested-shape failure observed live. Common prompts/taxonomies are contract-tested; provider wire guidance differs only to fit guided generation.

Actual local `SystemLanguageModel.default.availability` was **available**. Initial nested and guided attempts produced unknown metadata, copied allergen-code lists, self-dependencies and incomplete preparations. Flat fields improved basic output. The final flat-prompt basic sample generated all three measured ingredients; common normalization recovered explicitly supplied servings/prep/cook and derived the total. Its actual output is a permanent fixture, clearly labeled as captured Apple generation. Complex/out-of-order/canonical capability probes lost preparations and are **not live-model accepted**.

The production suitability gate therefore allows currently verified basic short preparations and routes long/multi-preparation input directly to consented cloud/manual. It does not repeatedly spend local/cloud calls trying a known-unsuitable shape. A rejected available Apple result may use the already-consented cloud fallback once; cancellation never falls back. Apple and manual entry are independent of provider throttling. No automatic cloud retry. Advanced on-device quality remains a genuine model limitation, not hidden behind compile-only claims.

Reproducible opt-in evaluation: compile `RecipeCreatorContract.swift` and `DevelopmentTools/evaluate_recipe_creator_apple.swift` with the installed Swift toolchain, then pass a safe JSON source corpus and temporary output path. No account, credentials, cloud, Recipe Save or user store is used. Actual availability, generation and quality are distinct. Current Apple documentation describes guided generation, availability and evaluation tooling: [Foundation Models](https://developer.apple.com/documentation/FoundationModels), [generation and testing](https://developer.apple.com/documentation/foundationmodels/generating-content-and-performing-tasks-with-foundation-models). No paid/remote Apple-model integration was introduced.
