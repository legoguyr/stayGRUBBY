# Backend MVP readiness rehearsal — November 17, 2026

**LEGO architecture verdict: CONDITIONALLY READY.** The repositories and runtime interfaces support changes within most domain boundaries. This milestone extended the existing publication path without app source changes or new data. Public launch still depends on separating private Food Bible access from a profile moderation decision, enforcing objectionable-content policy, proving signed and Storage paths, and establishing an operated response process.

The next private/social authorization change should keep the same owner-scoped RPCs. Use the live permanent-account resolver for private reads, saves, history, direct Recipe media and restore, with the usual lifecycle/account locks. Keep social eligibility on audience expansion, shared destinations, blocking and the staff queue. Prove that the same hidden-profile owner can still work with a private Recipe, that a peer cannot read its current or pinned Recipe or bytes, and that hidden/signed-out/deleting actors cannot publish or bypass existing checks. A one-line relaxation of the shared actor would reopen unrelated social paths. The inherited Recipe wrapper chain requires a dedicated focused security checkpoint before deployment.

## Practical extension

The predecessor rewrote an unchanged description in a separate transaction. The regression compares PostgreSQL tuple versions before and after the candidate, then tests a normalized repeat, a real edit, clearing twice, and retrying a prepare request. It also verifies a foreign caller and a hidden/draft post are denied, the existing post has the same identity, a permitted friend still sees its exact Recipe revision, and related cook, rank, Recipe and attachment rows are unchanged. The new migration changes one private implementation behind the existing public interface and introduces no storage policy, data copying, index or recurring write. This establishes a reusable extension path for publication metadata. It supplies no production write-volume estimate.

## Storage audit and measurement

At **9:05 a.m. Eastern on November 17**, the production target had a fresh empty signal set. The active five-minute monitor held 152,454,591 PostgreSQL-visible bytes, including 33,402,741 database bytes, 117,440,879 WAL bytes and 1,610,971 log bytes. The 43 product relations occupied about 3.37 MB. Private Storage held 114 objects and 18,695,557 bytes, with known sizes for every object. Sample rates showed zero app row changes per minute, zero excess rollbacks and no long or idle API transactions. A single sample cannot establish a growth trend. The exact-equivalent index catalog check found zero duplicate groups. It did not evaluate workload-dependent overlapping indexes or recommend dropping any. There were 161 sync receipts using 196,608 relation bytes, and 558 retained capacity-job runs within the existing bounded retention policy.

The last recorded Dashboard baseline was about 0.29 GB of the 2 GB disk, leaving about 1.71 GB **at that reading**. Confirm current full-disk and System headroom in the Dashboard. The PostgreSQL sample cannot measure Supabase-managed System bytes. The historic 1.6 GB incident belonged to the original project. Write protection already includes local fit and compare, bounded outbox retries, immutable idempotency receipts, unchanged-revision read avoidance and photo upload reconciliation. Receipts and retired IDs protect retry/restore. Keep their existing retention until a safe minimum-build and recovery contract can prove compaction. Growth in shared images, managed platform logs, and busy-hour reads remains a measurement question. None warrants deleting evidence, adding telemetry rows, or changing the plan during this milestone.

The capacity check reports warning, incident/critical and stale/unreachable states with one bounded read and no database writes. It is tested off production and ready to wire into an operator-managed external scheduler. Alert transport and owner receipt still need to be verified.
