## Auth transfer

Supabase supports logical SQL transfer of Auth data between projects. Use a reviewed subset of `auth.users` and `auth.identities` on the fresh managed schema. Supabase provides a general SQL restore procedure, so the exact filtered import below needs a rehearsal. Creating users with the Admin API or allowing email-based linking would not preserve the verified Apple mapping. [Supabase Auth migration guidance](https://supabase.com/kb/troubleshooting/migrating-auth-users-between-projects) · [Logical restore procedure](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore)

1. Build the retained user set from `provider = 'apple'` joined to `staygrubby.auth_account_links`. Verify eight distinct user UUIDs and eight identities, one identity per user, eight matching nonblank `provider_id` and `identity_data.sub` values, and one permanent account per user. Verify the only email identity matches `development.recipe_test_identity.auth_user_id`. Abort on a changed provider or ambiguous linkage. The eight Apple users had no password hash, one-time Auth token, nonzero instance ID, phone, SSO or superadmin status.
2. In one source repeatable-read, read-only snapshot, client-side `psql \copy` the selected `auth.users` rows and their `auth.identities` rows to an owner-restricted directory. Select explicit nongenerated columns using the checked source/target schema. Omit `users.confirmed_at` and `identities.email` because the target generates them. Omit session/refresh/MFA session records and one-time action token columns (`confirmation_token`, `recovery_token`, `reauthentication_token`, `email_change_token_new`, `email_change_token_current`, `phone_change_token`). Confirm the excluded token fields remain blank for retained users. Preserve source user UUID, identity UUID, provider subject, account metadata and timestamps. Keep CSV files and identity-subject checksums outside Git.
3. Use `psql -X` and `ON_ERROR_STOP=1` on the verified target. Load `auth.users` first, then `auth.identities`, using the same explicit column lists, before importing app accounts and `auth_account_links`. Target catalog confirmed matching managed column and constraint definitions, direct INSERT privilege for the DB operator on both tables and no noninternal triggers on those two target tables. Verify within the rehearsal and again on the actual target.
4. Configure Apple with the existing iOS bundle ID `com.guyrettig.StayGrubby` under the same Apple Developer team. The source enables Apple and disables email, phone and anonymous sign-in. The empty target starts with email enabled and Apple disabled. Disable email and keep target access closed during staging. Preserve the native Apple token audience and nonce handling. Verify the dashboard Client IDs and any redirect allowlist separately. Native token sign-in does not require a web OAuth client secret. The deletion function's Apple revocation credential is a separate requirement. [Apple provider setup](https://supabase.com/docs/guides/auth/social-sign-in/auth-apple)
5. Keep the target project's signing keys. Have an existing tester reauthenticate on the controlled target build after structural verification. Confirm the same Apple subject maps to the same Auth user and StayGrubby account, and provisioning creates no duplicate. Run the same test on a device with an existing local library and on a clean install. Compare identity fingerprints before owner sign-in changes Auth timestamps.

## Phase 2 ordering and integrity gates

1. **Owner preparation.** Verify both refs, target GitHub deployment rules and current source write posture. Authorize the rehearsal, import and cutover separately. Confirm accepted fixture exclusions, the orphan avatar and incomplete reservations, the managed Storage owner-field tradeoff, and old-client/update communications. Set up scoped TLS-verified libpq services and separate Storage access on the operator's machine. Keep DB credentials and exported data private. Keep source unchanged. If source is writable again, establish a separately authorized source freeze before the final export.
2. **Rehearse with disposable data.** Apply all 48 canonical migrations in order to a disposable PostgreSQL 17 Supabase environment. Check an empty target and reconcile the extra public RLS safety difference. Exercise an Auth/Apple identity-shaped fixture, selective import ordering, deliberate history preservation, a tombstoned cook, cross-owner authorization and Storage deletion. Use isolated target fixtures and no automated production writes. Capture the SQL, selection and expected counts before the live load.
3. **Prepare the actual target.** Confirm emptiness, apply only the 48 canonical migrations with no seed and verify migration versions/hashes. Use the explicitly identified target for any linked CLI operation. Reapply and verify the reviewed project-level settings and bucket configuration. Keep the app endpoint, public signup and general traffic closed through verification.
4. **Freeze and export.** Recheck the source read-only setting and owner-device pending work. Use a single snapshot with `BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY` and `SET LOCAL TIME ZONE 'UTC'`. Export explicit allowlisted columns via client-side `\copy`. Produce sorted per-table row counts and SHA-256 of deterministic row serialization, an Apple subject → Auth UUID → account UUID fingerprint, and per-object metadata. A subset export must also report what it excluded and why. Protect staged data with restrictive permissions and encrypted storage. Scan for cross-scope references before accepting the export.
5. **Import rows in one target transaction.** Load Auth first, then app accounts and links. Defer deferrable constraints. On application tables only, temporarily disable reviewed user triggers that would recalculate, synthesize history or emit events during import. Keep FK enforcement active. Restore original trigger enabled modes before commit. Use explicit column lists, preserve IDs and timestamps and abort the transaction on any failed constraint or digest. Start with account/identity, then base cooking and Recipe rows, then dependent history and social rows in the waves below. Do not import managed Storage metadata. Supabase creates it via the Storage API.
6. **Copy bytes and verify.** Upload the approved manifest via Storage API/S3 before opening any app access. Compare source/target SHA-256, byte length, key and MIME for every retained object. Reconcile all readiness fields, including historical Recipe photos. Deploy and verify approved Edge Functions and secure configuration. Run `DevelopmentTools/database_health.sql` and compare dashboard disk, connection health, retry-code checks, schema privileges, and provider settings. Validate permitted and denied access in the rehearsal before owner physical acceptance.
7. **Cut over only after sign-off.** Update the target URL/ref and its publishable key in the approved app configuration and deliver that build under a separate distribution instruction. An existing build embeds the old endpoint and cannot be switched remotely by importing data. Require testers to update and reauthenticate. Verify the unchanged Apple/Auth/account mapping, local library restore and pending sync, old receipt replay, original ranking/evidence, Recipe history, photo reads, Sous Chef graph and authorized The Pass publications. Open new signups only after acceptance and monitor Auth, sync, Storage, conflicts and disk health.

## Rollback and decision gates

Before target writes, keep release pointing at the original endpoint or withhold distribution if the original is read-only. If validation fails, keep the target closed and preserve the original project. A source endpoint rollback by itself does not restore service while that project is read-only. Once real writes occur on the target, freeze new writes and reconcile target-only cooks, evidence, Recipes and media before any endpoint reversal. Preserve both projects and the private manifest. Require separate authorization for any reverse transfer or source change. Avoid dual writes.

**Owner actions.** Confirm the target GitHub deployment behavior and hosted settings, securely configure Apple and Gemini material, authorize the rehearsal and later transfer, confirm unresolved retention and Storage ownership decisions, and coordinate the required client update and native Apple acceptance. Confirm old-client treatment because older builds still reference the source. Keep the old project available for recovery evidence.

**Open gates.** Target Auth and Storage byte parity have a documented path and still require rehearsal. Review 13 incomplete cook claims, the unreferenced avatar, managed Storage ownership expectations, and any unsynced device outboxes. The source's platform disk issue remains independent of this plan. An independent comparison of dashboard-only settings, current deployed function bundles and any target GitHub automatic deploy rules is required before production cutover.
