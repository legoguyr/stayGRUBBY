## Account-erasure blocker

On both the source-shaped and imported fixtures, the canonical erasure RPC refused to proceed while objects remained. The actual Storage API then removed the bytes from all four buckets by account path. After cleanup, `api.erase_account_data` failed with `23503` on `media_backups_account_id_media_id_fkey`. The account remained `deleting` and the job stayed at `storage_cleared`. The FK references `media` without a cascade and the erasure function deletes the account without removing the dependent manifests. The same FK and function are live on the source. Read-only counts found 57 manifest rows across five accounts and zero deletion jobs.

Deleting only the fixture account's manifest rows inside a diagnostic transaction allowed erasure to finish and preserved the peer account. The diagnostic transaction rolled back. Prepare a separately authorized, additive correction scoped to account deletion, then rerun the disposable end-to-end test with backed-up active and retired media, verify retry and peer isolation, and check the approved ledger again before any real data transfer. Preserve all manifest/history rows during normal migration. Keep existing Apple revocation and Storage gates.
